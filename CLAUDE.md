# TakeOne — contexto para o Claude

O Claude Code lê este arquivo sozinho ao abrir uma conversa nesta pasta. Ele resume o que já foi decidido e feito, para uma conversa nova continuar de onde a outra parou. O plano completo está em [docs/PLANO.md](docs/PLANO.md).

## Manter este arquivo atualizado

- Toda mudança que altera o estado do projeto atualiza, **no mesmo commit**, a seção "Estado atual" daqui e o checklist do `docs/PLANO.md`.
- Decisão técnica nova que não fica óbvia lendo o código vai para "Decisões técnicas" abaixo. Se for grande, vira um ADR em `docs/decisoes/`.
- Não repita aqui o que o código ou o plano já explicam. Este arquivo é o resumo e o "porquê".

## O que é

Editor de vídeo web no estilo CapCut: barra de ferramentas, painel de conteúdo, prévia, propriedades e linha do tempo de várias faixas. Roda no Nitro 5 do dono, ao lado do HolyCut, com modelos de IA abertos e sem custo por uso.

As referências são o CapCut (só funções e fluxo), o OpusClip e o Cut.Pro, analisados com o REA. O código pode vir do HolyCut e dos repositórios MIT/Apache da storytold (FilmCraft, LightCraft, EffectCraft, PhotoCraft, SoundCraft, VectorCraft). O que pode e o que não pode vir de cada um está na seção 1 do plano.

## Pedidos fixos do dono do projeto

- **Nada pago por enquanto:** nenhuma API, modelo ou serviço cobrado por uso. Tudo roda com modelos abertos na máquina.
- **Fora do escopo, não propor:** avatar de IA, personas, dublagem, clonagem de voz, lip-sync e correção de olhar.
- **Nada do CapCut além da ideia:** sem código, ícones, modelos, músicas, efeitos ou marca dele. Nomes de marcas de terceiros (CapCut, Lumetri, Premiere) não aparecem na interface.
- **O TakeOne é independente do HolyCut:** pode copiar código de lá, mas sem ligação por código compartilhado, banco ou login. O HolyCut não é alterado por causa do TakeOne.
- **O repositório é público.** O `.env` nunca vai para o Git. Antes de cada push, procure no diff por senhas, tokens, chaves e e-mails pessoais.
- **Tudo em português:** código, mensagens da interface, logs, testes e commits.
- **Stack aprovado:** FastAPI, Next.js 16 com Tailwind 4, MongoDB, FFmpeg e Docker Compose. Python com pymongo, `logging` em vez de `print`, fuso `America/Sao_Paulo` e scripts com `argparse --agora --automatico`. **Proibido** usar Redis, bancos SQL e ORM. A fila de jobs roda no próprio Mongo.
- **Git:** identidade local `Joshua Maciel <JoshuaMaciel337@users.noreply.github.com>`. Mensagens no formato "Área: descrição curta.", com acento, um corpo curto dizendo o porquê e o trailer `Co-Authored-By` do Claude. Commits pequenos, um por área, direto na `main`.
- **Licenças:** só bibliotecas e modelos com licença permissiva (evite AGPL). Música só com licença. Código portado do FilmCraft ou do LightCraft segue as regras do [THIRD_PARTY.md](THIRD_PARTY.md).
- **Prévia igual ao render:** toda diferença entre a prévia no navegador e o vídeo exportado é medida em números, não só no olho.

## Arquitetura em um minuto

- `apps/api` (FastAPI), `apps/worker` (fila), `apps/web` (Next.js) e `core` (config, Mongo, fila, storage, FFmpeg, compartilhado entre API e worker).
- **Fila no Mongo:** o job tem lease e heartbeat, e o de prioridade maior sai primeiro. `ErroDefinitivo` manda o job para erro sem novas tentativas. Uma tarefa é `Tarefa(executar(db, job, reportar), ao_falhar)`, registrada em `REGISTRO` (`apps/worker/tarefas/__init__.py`) e em `TAREFAS` (`core/modelos/job.py`).
- **Eventos ao vivo:** por SSE, sempre começando com o evento "pronto". Se ele não chegar em 5 s, o site passa a consultar a API a cada 3 s, porque o Quick Tunnel da Cloudflare não entrega SSE.
- **Upload:** tus 1.0.0 dentro da própria API, em pedaços de 8 MB ([ADR 0001](docs/decisoes/0001-upload-tus-na-api.md)).
- **Arquivos:** o resto do sistema só conhece "chaves" (`org_<id>/midias/<id>/...`). Trocar a pasta local por R2 ou S3 é trocar o `core/utils/storage.py`.
- **Isolamento:** toda consulta filtra por `organizacao_id`. Cada espaço só vê o que é dele.

## Decisões técnicas que não aparecem de cara no código

- **Portas:** Mongo 27019, API 8010, site 3010 e ComfyUI 8188, no Compose e no `npm run dev`. As do HolyCut (27018, 8000, 3000) ficam livres, porque os dois rodam no mesmo Nitro 5. O backup sai às 03:30, meia hora depois do HolyCut.
- **Licenças em `licencas/`, não na raiz:** os `LICENSE-*` do FilmCraft e do LightCraft têm o copyright do ArtCraft Team. Na raiz, pareceriam a licença do TakeOne inteiro.
- **Organização se chama "espaço" na interface.** No cadastro, o nome é opcional; sem ele, vira "Espaço de <primeiro nome>".
- **Editor:** a lista de mídias fica no `Editor` (um `useMidias` só), e a seleção guarda o id. Assim a prévia e as propriedades acompanham a ingestão sem recarregar.
- **Edição é pura:** as operações de `lib/projeto/edicao.ts` nunca alteram o projeto recebido e lançam `ErroEdicao` com a mensagem para a pessoa. Toda mudança passa por um `Comando` (`comandos.ts`); o histórico guarda os projetos de antes. Durante um arrasto, a linha do tempo aplica o comando a cada movimento e mostra o resultado, sem registrar no histórico. Os controles dos painéis comparam o valor solto com a tela, que já tem a prévia; quando mandam `null` ("igual"), o editor transforma a prévia em comando (`preverDoPainel`).
- **Nome e versão fora do histórico:** desfazer não desfaz o nome do projeto nem volta a `versao` do servidor. O PUT manda a versão que o editor conhece; se o banco tiver outra, a API responde 409 e o editor para de salvar e pede para recarregar.
- **Rascunho no navegador** (`takeone-rascunho-<id>`): só é aplicado ao abrir se foi feito sobre a mesma versão que o banco tem. Se outra aba salvou depois, o rascunho é descartado.
- **Prévia:** um elemento por faixa + mídia, para as duas metades de um clipe dividido usarem o mesmo vídeo sem engasgar. O próximo clipe da faixa já fica montado (escondido) 2 s antes de entrar. O vídeo só é reposicionado quando se afasta mais de 0,3 s do relógio.
- **Arrastar da biblioteca:** o id da mídia vai no nome do tipo do `DataTransfer` (`application/x-takeone-midia-<id>`), porque durante o arrasto o navegador só deixa ler os tipos.
- **Posição do clipe em frações do quadro:** `x` e `y` deslocam o centro em frações da largura e da altura do quadro, e `escala` 1 é a mídia inteira cabendo no quadro. Assim o mesmo projeto vale na prévia pequena e no render em 720p, 1080p ou 4K. A conta está em `lib/projeto/geometria.ts` e `core/utils/geometria.py`, e os dois leem os casos de `tests/casos/geometria.json`. Mudou a conta, mude os dois e os casos.
- **Prévia em canvas:** o canvas desenha a cada quadro da tela enquanto toca e, parado, só quando algo muda. Se uma camada ainda não tem quadro, a prévia mantém o desenho anterior por até 400 ms, para não piscar.
- **Quadros pelo WebCodecs:** o decodificador lê do proxy só o cabeçalho (mp4box) e depois cada grupo de quadros por Range, e decodifica a partir do quadro-chave anterior. O tempo de cada quadro desconta a lista de edição (`elst`), como o FFmpeg faz. Guarda poucos `VideoFrame` abertos, porque o decodificador trava com muitos. Se o WebCodecs falhar (navegador sem ele, arquivo que o leitor não entende), aquele clipe volta para um `<video>` escondido, que pode errar o quadro por um.
- **Som separado da imagem:** o som de todo clipe sai de um `<audio>` próprio, ligado a um ganho do Web Audio (`lib/previa/audio.ts`), que segue o relógio do editor. O contexto de áudio só nasce quando a pessoa aperta reproduzir, porque o navegador exige um gesto.
- **Mudança provisória:** arrastar na prévia ou num controle deslizante do painel muda um `Comando` provisório no `Editor`, que só aparece na tela. Ao soltar, vira comando de verdade e um passo do desfazer.
- **Render:** cada clipe é uma entrada do FFmpeg aberta só no trecho dele (`-ss`/`-t` antes do `-i`), sobreposta num quadro de cor com `overlay format=rgb`, como a mistura do navegador. O clipe aparece com `gte(t, início - meio quadro) * lt(t, fim - meio quadro)`, para nenhum quadro cair bem na fronteira. São no máximo 400 clipes por exportação, porque cada um é um arquivo aberto ao mesmo tempo.
- **Exportação guarda uma cópia do projeto:** editar enquanto o vídeo é gerado não muda o que sai. O link do celular é o do HolyCut: token de 24 h, com só o hash no banco.
- **Texto é imagem do servidor:** o PNG do texto vem de `core/utils/texto.py` (Pillow, motor de layout BASIC, fontes em `core/fontes`), pedido pela prévia em `/api/textos/imagem` e gerado de novo pelo worker no render. A prévia pede sempre com lado menor 1080 (`LADO_REFERENCIA_TEXTO`); o render desenha no tamanho do vídeo, para ficar nítido em 4K, mas estica a imagem até a caixa medida em 1080. Assim o texto fica no mesmo lugar nos dois, mesmo com a medida das letras mudando 1 a 2% entre tamanhos.
- **Clipe de texto não tem mídia:** `midia_id` é `null` e o clipe tem `texto`. Ele só fica em faixas `texto`, que ficam sempre acima das de vídeo. Não há quebra automática de linha: as linhas são as que a pessoa digitou.
- **Legendas são textos:** cada legenda é um clipe de texto numa faixa `legenda`, que fica sempre acima das de texto (e estas acima das de vídeo). Aparecem e saem no vídeo pelo mesmo caminho dos textos. O estilo do painel vale para as novas e pode ser aplicado a todas as da faixa (`legenda.estilo`), sem mudar o conteúdo.
- **Animações:** `transformacaoAnimada` (TS) e `transformacao_animada` (Python) fazem a mesma conta, conferida pelos casos de `tests/casos/animacao.json`; o teste do Python também roda as expressões do FFmpeg nos mesmos casos. A opacidade é linear porque o render usa o `fade` com alfa. As alças da prévia mexem na posição sem animação. Os loops são senos do tempo desde o começo do clipe; no render, o pulsar faz a caixa nascer no maior tamanho (`base_do_render`) e só diminuir por quadro, e o balançar usa o mesmo `rotate` por quadro dos keyframes de giro.
- **Cor:** `aplicarCor` (TS), o shader do compositor e `aplicar_cor` (Python) fazem a mesma conta; os casos de `tests/casos/cor.json` saem do Python e o TS confere. No render, a conta vira uma LUT 3D de 33 pontos (`lut3d`, interpolação tetraédrica) e a vinheta vira uma imagem cinza multiplicada ao clipe (`blend` multiply), para não escurecer o fundo transparente dos textos. Medido no Chrome: o shader fica a menos de 1/255 da conta.
- **Transições:** ficam no clipe que sai (`transicao`) e cobrem o corte pela metade. Na janela, os dois clipes aparecem: a prévia pede à mídia instantes antes ou depois do clipe (o decodificador segura no primeiro ou último quadro), e o render lê a sobra com `-ss`/`-t` e repete quadro com `tpad` quando não há. O som não muda: cada clipe soa só entre o começo e o fim dele (no render, `atrim` pula a sobra lida). A conta está em `lib/projeto/transicao.ts` e `core/utils/transicao.py`, com os casos de `tests/casos/transicao.json`.
- **Letra a letra é uma máscara:** o PNG do texto continua um só; a API manda junto (`X-Layout-Texto`) onde fica cada letra, em frações da imagem, e só o trecho de letras [de, ate) aparece. A prévia esconde o resto no shader; o render usa quatro `drawbox` transparentes (`replace=1`) que um roteiro do `sendcmd` move quando o trecho muda. O destaque da fala é uma segunda imagem, na cor do destaque e sem fundo nem sombra, por cima do texto, com a mesma máscara. A conta está em `lib/projeto/letras.ts` e `core/utils/letras.py`, com os casos de `tests/casos/letras.json`. Os tempos das palavras ficam no texto (`tempos`, desde o começo do clipe) e andam junto ao aparar, dividir e cortar trechos; sem eles (legenda digitada), as palavras dividem a duração pelas letras.
- **Abaixar na fala é uma curva gravada:** como o "Seguir o rosto", a conta (`lib/projeto/abaixar.ts`) roda uma vez no editor, a partir das palavras transcritas das outras faixas, e fica no clipe (`abaixamento`: fator de 0 a 1 por instante). A prévia multiplica o ganho por ela a cada quadro; o render passa a curva por um roteiro do `asendcmd` para um `volume`, em blocos de 10 ms (`asetnsamples`). Mudou a fala, a pessoa refaz. Falas separadas por menos de 0,8 s viram uma só, e o som desce 0,3 s antes e volta em 0,5 s.
- **Efeitos de voz iguais por construção:** o equalizador usa os filtros do FFmpeg (`lowshelf`, `equalizer`, `highshelf`) com as fórmulas do "Audio EQ Cookbook", as mesmas do `BiquadFilterNode`; o eco é a mesma soma de três atrasos (`aecho` e `DelayNode`); o reverb é a mesma convolução, com a resposta ao impulso gerada em `core/utils/som.py` (semente fixa), servida à prévia em `/api/som/reverb.wav` e usada sem normalizar nos dois (`afir irnorm=-1`, `ConvolverNode.normalize = false`). Os efeitos ficam depois da velocidade e antes do volume, como os nós da prévia entre o elemento e o ganho.
- **Desfoque:** o sigma é uma fração da altura do clipe. A prévia desfoca a textura em duas passadas num framebuffer (lendo um nível menor do mipmap quando o sigma passa de 4 pixels) antes de desenhar a camada; o render usa o `gblur` (steps=6) com bordas repetidas antes (`pad` + `fillborders`) e cortadas depois, porque o `gblur` sozinho erra nas bordas da direita e de baixo. Com transparência (textos), o desfoque é no alfa pré-multiplicado nos dois. O sigma que muda por quadro vai num roteiro do `sendcmd`, com `sigma` e `sigmaV` (só o `sigma` deixava o vertical parado).
- **Curvas:** cúbica monótona (Fritsch–Carlson) pelos pontos, a mesma em `lib/projeto/cor.ts` e `core/utils/cor.py` (casos em `tests/casos/curvas.json`), aplicada depois dos ajustes e antes da vinheta: a curva geral nos três canais, depois a de cada canal. No render ela entra na mesma LUT 3D; na prévia, o shader lê uma tabela de 256 tons por canal.
- **Mesclagem:** na prévia, cada modo é uma função de mistura do WebGL com a opacidade já na cor (multiplicar sai misturado ao branco; os fragmentos fora da cortina ou das letras são descartados, não pintados de transparente, porque no multiplicar o transparente escureceria). No render, a camada é achatada num quadro da cor neutra do modo (branco no multiplicar, preto na tela e no somar) e misturada com o `blend` do FFmpeg: a mesma conta.
- **Efeitos de vídeo:** os números ficam em `lib/projeto/efeitos.ts` e `core/utils/efeitos.py`. O desfoque do efeito soma ao das transições (mesmo caminho). O brilho, na prévia, é uma segunda cópia desfocada (framebuffers 2 e 3, unidade de textura 2) somada em "tela" no shader; no render, um `split`, o mesmo `gblur` e um `blend=screen`, no alfa pré-multiplicado, antes da cor. O olho de peixe é o `lenscorrection` (k1) com um zoom de 1 + k1 no meio para não sobrar canto; a prévia faz a mesma troca de coordenadas no shader (medido: a lente do FFmpeg fica a uns 2,5 níveis em 255 da conta numa imagem difícil).
- **VHS e glitch:** o vermelho e o azul andam para lados opostos (`rgbashift` no render, duas leituras deslocadas no shader); no glitch, o desvio muda em blocos de 3 quadros, sorteados por um hash de inteiros (`hash32`) que dá o mesmo resultado no TS e no Python (seno de ponto flutuante poderia variar). As linhas do VHS entram na imagem multiplicada da vinheta; a cor desbotada do VHS soma aos ajustes de cor do clipe (`ajustes_do_efeito`). Casos em `tests/casos/efeitos.json`.
- **Luz e granulação:** só em clipes de mídia (com transparência, a "tela" e o `grainmerge` mudariam o transparente). A luz é uma faixa gaussiana que atravessa o clipe a cada 4 s: no render, uma tira 3 vezes mais larga que o clipe, recortada por quadro (`crop` com expressão do tempo) e somada com `blend=screen`. O grão é uma imagem fixa de 2048 × 1080 células sorteadas (`sorteio(linha × 2048 + coluna)`); a cada quadro um recorte sorteado (sendcmd no `crop`) cresce até o clipe (`scale neighbor`) e entra com `blend=grainmerge`. A prévia monta a mesma imagem no navegador.
- **Tela verde pelo `colorkey`, não pelo `chromakey`:** o `chromakey` mede a cor em YUV numa vizinhança 3 × 3 (difícil de repetir no shader); o `colorkey` mede a distância em RGB, pixel a pixel, e o shader faz a mesma conta. Ele troca o alfa (não multiplica), por isso vale só em mídia, cujo alfa nesse ponto ainda é 1.
- **Velocidade com curva:** a curva (u, s) só redistribui o tempo: `velocidade` é a média, a duração e o trecho da mídia não mudam (`lib/projeto/velocidade.ts` e `core/utils/velocidade.py`, casos em `tests/casos/velocidade.json`). No render, o vídeo passa por `settb=1/90000` (sem ele o setpts arredondava para a grade da mídia), um `setpts` com a inversa da conta (reta entre 96 amostras) e `fps` com `round=up`, que mostra o último quadro que chegou, como o decodificador da prévia (medido: 118 de 120 quadros iguais). O som passa por `atempo` que recebem o andamento por roteiro, só os que fazem falta (em série eles perdem o fim do som). Aparar, dividir e cortar recortam a curva. Não combina com transição: a edição tira a transição e a API recusa.
- **Tom da voz é um arquivo, como a voz limpa:** o Web Audio não muda o tom sem mudar a velocidade, então o worker gera `tom_p3.m4a` (ou `tom_m2_limpa.m4a`, sobre a voz limpa) no tempo exato da mídia e a prévia e o render tocam o mesmo arquivo. Os nomes saem de `chave_do_tom` (Python) e `chaveDoTom` (TS); a API só serve esses nomes (`arquivo_publico`).
- **Recorte do fundo é uma máscara em vídeo:** o MODNet (Apache-2.0, ONNX pelo onnxruntime na CPU, 16 threads, uns 65 ms por quadro a 256 pixels) roda nos quadros da cópia leve, a mesma que a prévia decodifica, e a máscara sai em `mascara.mp4` (cinza, 360 no lado menor, no ritmo da cópia leve). A prévia decodifica a máscara junto com o vídeo (outro `DecodificadorDeVideo`) e multiplica o alfa no shader; o render lê o mesmo trecho dela e usa o `alphamerge` depois do desfoque e antes da lente, como o shader. O OpenCV não abre esse ONNX (formas dinâmicas), por isso o onnxruntime. O modelo é de retrato: recorta pessoas, não objetos.
- **Imagem sem ruído é um par de arquivos:** como a voz limpa, o worker gera `limpo.mp4` (resolução cheia, já em BT.709 marcado, só para o render) e `limpo_proxy.mp4` (a cópia leve dele, que a API serve à prévia). O render abre o limpo como mais uma entrada só para a imagem; o som segue no original. O filtro (`hqdn3d=10:8:12:10`) foi escolhido medindo: tira metade do ruído e o vídeo limpo perde 2,3 níveis de detalhe.
- **Quadro da mídia no render é o último que chegou:** o `fps` de todo clipe usa `round=up`, a regra do decodificador da prévia. Com o padrão (o mais próximo), um vídeo de 29,97 num projeto de 30 saía sempre um quadro adiantado (1 de 200 quadros iguais; com `round=up`, 200 de 200). Os vídeos de teste a 30 exatos escondiam isso.
- **CI com FFmpeg 6:** o CI instala o FFmpeg do Ubuntu (6.1); o worker usa o 7. Filtro ou opção nova precisa existir nos dois (o `afir` do 6 não tem `irnorm`). Para conferir antes do push: rodar o pytest num `ubuntu:24.04` com o `ffmpeg` do apt.
- **Fades:** `fade_entrada` e `fade_saida` em ticks, sempre somando no máximo a duração do clipe (a edição encolhe os fades ao aparar). Ao dividir, o fade de entrada fica com a primeira metade e o de saída com a segunda.
- **Tick em `number`:** exato até cerca de 9 h 50 min; o projeto vai até 6 h. Contas com taxa de quadros são feitas em BigInt (`BigInt(0)` em vez de `0n`, porque o alvo do TypeScript é ES2017).
- **Som do render em duas passadas:** a primeira mistura o som de todos os clipes num `som.mka` (ponto flutuante) e mede o loudness com o `ebur128`; a segunda gera o vídeo com essa mistura, um ganho fixo até -14 LUFS e o `alimiter` só nos picos. O `loudnorm` numa passada mexia no ganho ao longo do vídeo (uma introdução 26 dB mais baixa saía só 1 dB abaixo do resto) e, sem ele, o grafo único travava no FFmpeg 7 em projetos com transição.
- **Cor sempre em BT.709:** vídeo sem marcação de cor é lido como BT.709, como o Chrome faz na prévia (`ler_como_bt709`, com a matriz guardada pela ingestão em `video.matriz`). O proxy e o vídeo exportado saem convertidos para BT.709 e marcados (`MARCAS_BT709`). Sem isso, a marcação do arquivo final mudava conforme o grafo (com vinheta saía BT.601) e cada player mostrava uma cor. HDR (BT.2020) ainda não é convertido.
- **Worker de GPU sem PyTorch:** a transcrição usa só o faster-whisper (ctranslate2 com o cuBLAS e o cuDNN 9 do pip), sem o WhisperX do HolyCut: o tempo por palavra dele basta para as legendas e a imagem fica menor. A placa é dividida com o HolyCut (cada um com a sua fila); o Whisper usa uns 3 GB de VRAM. Cada transcrição roda num processo filho (spawn) que termina no fim do job, porque o processo do worker não devolvia uns 2,5 GB de RAM depois de soltar o modelo.
- **Wan 2.2 medido no Nitro (14/10/2026):** 5 s em 832×480 (121 quadros a 24 fps, 20 passos, pesos em fp8) levou 12 min 43 s, dos quais 10 min 40 s gerando (32 s por passo). Pico de 9,7 GB de RAM, 7,8 GB de VRAM e 81 °C na placa. Precisou de 12 GB de RAM no WSL (`%USERPROFILE%\.wslconfig`, com 8 GB de swap) e do HolyCut parado: com 7,4 GB o Docker inteiro travou. Os pesos ficam no volume `takeone_comfyui_modelos` (ler da pasta do Windows dava `errno=12`).
- **Geração de vídeo pelo ComfyUI:** o ComfyUI (GPL-3.0) é o serviço `comfyui` do Compose, no perfil `video`, sem porta para fora; o worker de GPU monta o grafo (`core/modelos/geracao.py`), manda por HTTP, acompanha pelo `/history` (o progresso é o tempo passado sobre o estimado, porque o passo a passo só sai pelo websocket) e baixa o MP4 pelo `/view`. Antes de começar, espera até 30 min por 6,5 GB de VRAM e 6,5 GB de RAM livres (sem contar os 2,5 GB que o ComfyUI parado já ocupa e reaproveita) (`/system_stats` e `/proc/meminfo`, que no Docker do Windows é a memória do WSL inteiro): sem isso o Docker travava. No fim pede `/free` para soltar o modelo. A mídia nasce na API com status "processando" e o `job_ingestao_id` apontando para o job da geração, para o cartão mostrar o progresso sem código novo; o worker troca pelo job da ingestão quando o vídeo fica pronto.
- **Animação em HTML é uma mídia com transparência:** em vez de um tipo novo de clipe, cada animação vira uma mídia da biblioteca (`animacao` no documento), com o vídeo da cor (`original.mp4`) e o da transparência (`mascara.mp4`, no formato da máscara do recorte do fundo). O clipe dela nasce com `remover_fundo` ligado e numa faixa de sobreposição, então prévia, render, keyframes, efeitos e animações de entrada funcionam sem código novo. Os modelos (`core/animacoes/*.html`) são só CSS, sem GSAP; o worker pausa `document.getAnimations()` e avança o relógio quadro a quadro num Chromium sem tela (Playwright), a 30 fps e com o lado menor em 1080. Antes do H.264, a cor das bordas é espalhada para os pixels transparentes em volta (média pesada pelo alfa, numa cópia 4 vezes menor), senão as letras ganhavam contorno escuro. A prévia do painel é a mesma página num iframe só com scripts (`sandbox="allow-scripts"`), por isso as fontes de `/api/animacoes/fontes` são públicas e com CORS. A ingestão agora guarda os arquivos que já estavam na mídia antes dela.
- **O LLM só aponta palavras:** o "Criar automaticamente" manda ao Qwen3 a fala já limpa, com cada palavra numerada, e a resposta vem presa a um esquema JSON (`format` do Ollama, `think` desligado). Título, tarja, zooms e chamada apontam números de palavras, então o tempo sai da transcrição. `conferir_plano` (`core/modelos/direcao.py`) descarta o que não se sustenta: índice fora da fala, trecho curto, longo ou sobreposto, nome que não está na fala perto da palavra apontada e chamada com mais de 6 palavras (o modelo de 8B tende a copiar a frase falada). O Ollama é o serviço `ollama` do perfil `gpu`, sem porta para fora; o worker baixa o modelo no primeiro pedido e pede `keep_alive` 0, para a placa voltar ao Whisper e ao Wan no fim de cada plano.
- **Biblioteca de animações:** cada modelo é um arquivo `core/animacoes/<id>.html` com os dados num bloco JSON (nome, categoria, duração, motor, campos, `tela_cheia`), lido na importação; acrescentar modelo não mexe em Python. Dois motores: "css" (o worker pausa e avança `document.getAnimations()`) e "canvas" (o modelo define `window.renderAt(t)`, função pura do tempo, em Canvas 2D, SVG ou Three.js). O `comum.js` dá as curvas, a mola, o sorteio com semente e as ajudas de texto; o Three.js 0.186 fica em `core/animacoes/vendor` (os módulos não carregam de `file://`, por isso o worker serve a página num servidor HTTP só dele, em 127.0.0.1, e o Chromium não fala com mais nada). WebGL roda em software (SwiftShader) e o Canvas 2D na CPU (`--disable-accelerated-2d-canvas`: pelo SwiftShader, as partículas levavam 4,2 s por quadro; assim, 0,4 s). Quadro todo coberto (meio de uma transição) chega do Chrome em PNG sem alfa e vira opaco. As miniaturas de transição usam o quadro de 25%, porque no meio a tela é uma cor só. Modelo que desenha texto num canvas espera `TO.carregado` (as fontes) pelo `window.prontoParaGravar`. `tests/test_biblioteca_animacoes.py` abre cada modelo em três proporções: sem erro de script, algo no meio, nada na borda (a menos que seja tela cheia) e o mesmo quadro para o mesmo instante. As miniaturas do painel saem de `apps/worker/miniaturas_animacoes.py`. Os temas (`core/animacoes/temas/<tema>.json`) são versões de um desenho com outros textos, cores e duração: cada uma vira o modelo `<tema>-<id>`, com miniatura própria, e o teste confere em 9:16 se os textos cabem (no CI, uma versão a cada quatro; `TAKEONE_TESTAR_TUDO=1` testa todas). O "Descreva a animação" escolhe só entre os desenhos (`DESENHOS`), para a lista caber no contexto do Qwen3. A API manda a lista de modelos já comprimida (montada uma vez, uns 10% do tamanho), sem compressão no resto da API, para não atrapalhar o SSE.
- **Palavras-chave ficam no PNG do texto:** o destaque da fala é uma faixa contínua de letras que muda com o tempo e não serve para palavras soltas. As palavras-chave (`palavras_chave`, números contados como em `palavrasDoTexto` e `palavras_do_texto`: sequências sem espaço, linha a linha) são desenhadas por `desenhar_texto`: o texto é desenhado de novo na `cor_chave` e colado só nas faixas das palavras, então o contorno, a sombra e o lugar das letras não mudam, e a prévia e o render usam o mesmo PNG. O LLM só aponta números; `conferir_escolhas` tira o que não existe e as palavras vazias (artigos, preposições, "que", "é"). No "Criar automaticamente", as palavras-chave são pedidas antes de criar as legendas, que já nascem pintadas.
- **Animação descrita é limpa duas vezes:** o worker de GPU limpa o que o LLM devolve (`separar_resposta` em `core/modelos/animacao_descrita.py`: só tags de texto e de SVG, sem script, eventos, `url()`, `@import` nem `@font-face`, classes sem ponto corrigidas, regras de `body` e `html` tiradas) e o modelo `livre` de `animacao_html.py` limpa de novo ao montar a página, porque ela abre no worker e no iframe do painel. Na gravação o Chromium só lê arquivos locais (o resto é abortado) e animação que não mostra nada em quadro nenhum é recusada. As funções do Ollama ficam em `apps/worker/tarefas/llm.py`, para o diretor e a animação descrita.
- **Comandos em sequência:** o `executar` do `useProjeto` parte de uma ref com o projeto mais novo, não do da última renderização. Antes, dois comandos no mesmo instante (legendas e zooms do "Criar automaticamente") partiam do mesmo projeto e o segundo apagava o primeiro.
- **Cópia leve de vídeo acima de 30 fps:** a ingestão reduz com `fps=30:round=up` (`reduzir_quadros`), a regra do render. Com o `-fpsmax` sozinho (o quadro mais próximo), um vídeo de 46 fps ficava com o quadro vizinho na prévia (5 a 13 níveis em 255; com a regra, 2,5 a 3). As mídias acima de 30 fps ingeridas antes disso só se corrigem ingerindo de novo.
- **Remover intervalos fecha o espaço em todas as faixas:** a limpeza de fala e a edição pelo texto tiram o mesmo trecho de tempo da linha inteira, para legendas, sobreposições e música continuarem com a fala. Um clipe cortado vira pedaços; o primeiro guarda o id e o que é de entrada (fade, animação), o último o que é de saída e a transição.
- **Fala no tempo da linha:** `lib/projeto/fala.ts` leva as palavras da mídia para cada clipe (trecho e velocidade) e é a base das legendas automáticas e da limpeza. Na transcrição, o worker tira das pontas de cada palavra o que é silêncio nos níveis da ingestão (`aparar_no_silencio`), porque o Whisper estica as palavras para dentro das pausas. Os vícios são só hesitações: "é", "um", "tipo" e "então" também são palavras normais em português.
- **Voz limpa sem PyTorch:** o DeepFilterNet roda pelo binário `deep-filter` do próprio projeto (Rust, com o modelo dentro), baixado no `worker.Dockerfile` com o SHA-256 conferido, e também no CI. Com `-D` a saída fica no tempo do original (medido 0 ms); o arquivo é completado até a duração da mídia, porque o filtro corta uns 30 ms do fim. Na prévia, o som com voz limpa é outro `<audio>` (outra chave), para não recarregar ao trocar de clipe.
- **Retake é por palavras, com fronteiras:** a tentativa começa num início de frase (depois de ponto ou de 0,3 s de pausa) e a versão boa recomeça depois de pontuação ou de 0,25 s de pausa, repetindo pelo menos 2 palavras; conta se a tentativa é repetida inteira ou se foi abandonada sem fim de frase. Sem as fronteiras, pares comuns ("do Premiere") viravam retake falso. Os cortes de `removerIntervalos` vão para o começo do quadro nas duas pontas, para não sobrar pedaço da palavra cortada.
- **Seguir o rosto:** a detecção é do YuNet no OpenCV (modelo MIT, baixado com checksum na imagem do worker), não do MediaPipe do plano: é um arquivo de 230 KB e roda no worker de CPU sem GPU. A busca é por mídia (coleção `rostos`), uma vez só; o caminho da câmera é feito no navegador, porque depende do clipe e do quadro do projeto. A câmera imita um operador: parada enquanto o rosto fica a menos de 4% do quadro, e um movimento só, com curva suave, até onde ele para. Antes, uma mediana de 3 amostras tira os picos da detecção e rostos com menos de 35% da área típica são ignorados (ícones e gente ao fundo puxavam a câmera). No máximo 100 pontos por eixo: a margem dobra até caber.
- **Keyframes no render:** a caixa do clipe sai da transformação de base (`transformacao_de_base`: a maior escala dos pontos, para redimensionar uma vez só e diminuir por quadro sem perder nitidez). Posição e escala viram expressões que somam às das animações e transições; a rotação vira um `rotate` com expressão e saída na diagonal; a opacidade vira um roteiro do `sendcmd` para o `colorchannelmixer`, um valor por quadro, porque o `geq` seria lento. O `rotate` pinta o que sobra de transparente (`c=black@0`): com `c=none`, o giro animado deixava rastro. Os tempos dos pontos são da linha do tempo, desde o começo do clipe; aparar o começo, dividir e cortar trechos deslocam os pontos para o movimento continuar igual.
- **GSAP só na home:** a home v2 usa GSAP 3.13 (ScrollTrigger e SplitText) e o Lenis (MIT), pelo npm, num import dinâmico em `componentes/inicio/movimentoDaInicio.ts`, e desfaz tudo ao sair da página. A licença do GSAP é gratuita e permite sites, mas proíbe ferramentas visuais de montar animação: por isso ele nunca entra no editor nem nas animações do vídeo (essas são só CSS). As letras dos botões são montadas no servidor (`Rotulo`), não pelo script, para o React não perder o controle do DOM.
- **Temas:** as cores ficam nos tokens `--to-*` do `globals.css`; o tema claro só troca esses tokens sob `:root[data-tema="claro"]`. Um script do layout (`lib/tema.ts`, `beforeInteractive`) põe o `data-tema` guardado no navegador antes da pintura, para não piscar. Cor fixa (branco, preto) só em cima do vídeo e das fotos. A home tem o CSS dela (`componentes/inicio/inicio.css`) inteiro dentro de `.inicio`, com as animações renomeadas (`inicio-*`), para nada vazar para o editor; o script do protótipo virou `AnimacoesDaInicio`, que só troca classes e textos da página desenhada no servidor. Os planos, o assistente de IA, os templates e o corte inteligente da home são do protótipo do kit e ainda não existem no produto: levam a tag "Em breve" (`EmBreve`), que sai quando cada um chegar.
- **Testes do site:** `npm test` usa o `node --test` com `--experimental-strip-types`. Por isso os arquivos de `lib/tempo.ts` e `lib/projeto/` importam uns aos outros pelo caminho relativo com `.ts`, sem o alias `@/`.
- **Lint do React 19:** a regra `react-hooks/set-state-in-effect` acusa `setState` depois de `await` dentro de um efeito. Use `.then()`, como em `useMidias`. Props que recebem um ref terminam em `Ref`, senão a regra `react-hooks/immutability` reclama ao atribuir.
- **Next.js 16:** o middleware é `proxy.ts`. O Next guarda na memória o corpo de toda requisição a `/api` e corta em 10 MB; os vídeos passam porque o tus manda pedaços de 8 MB.

## Rodar e testar

- Tudo: `docker compose up --build`, com o site em http://localhost:3010. Portas e pasta de armazenamento ficam no `.env` (veja o `.env.example`).
- Com a transcrição e o "Criar automaticamente": `docker compose --profile gpu up --build -d` (sobe também o Ollama; o primeiro plano baixa o Qwen3 8B, uns 5 GB). Para gerar vídeo, junte `--profile video` (sobe o ComfyUI; na primeira vez ele baixa uns 17 GB de pesos). Sem o worker de GPU, o pedido de legendas fica "na fila". No modo simulado (`MODO_IA=simulado`), um worker comum com `--recursos gpu` gera palavras de exemplo.
- Python: `ruff check .` e `pytest`. Os testes de integração criam um banco `takeone_teste_*` e o apagam no fim, e o `conftest` recusa qualquer outro banco.
- Os testes com FFmpeg são pulados quando ele não está instalado. Em Windows sem FFmpeg, rode-os dentro da imagem do worker.
- Site: `npm run lint`, `npm run typecheck`, `npm test` e `npm run build`, dentro de `apps/web`.
- Para mexer no site com a pilha no Docker: `next dev -p 3011` com `API_URL_INTERNA=http://localhost:8010`. O cookie de sessão vale para as duas portas.
- O CI (GitHub Actions) roda lint e testes do Python, com FFmpeg, e lint, tipos, testes e build do site. Todo push precisa terminar verde.
